# 答辩问答准备

> 面向评委（高校老师 + 企业工程师）可能追问的问题。每个问题先给一句话结论，再给展开，最后标出可能的追问方向。

---

## Q1. 这个工具和直接在群里问学长，有什么区别？

**一句话**：学长给的是「我记得」，这个工具给的是「原文怎么写的 + 去哪核实 + 你够不够格」。

展开：

- 群聊信息是**异步、易失真、不可检索**的。同一赛事三个版本的说法，人脑无法同时记住并比对。
- 工具做的是三件人做不到的事：**保留字段证据摘录供人工对照**、**跨来源比对冲突**、**按你的画像算匹配度**。
- 它不替代人做决定，替代的是「翻十几条群消息 + 打开三个网页核对」这段体力活。

可能的追问 → 「那你这不就是个搜索？」答：搜索给你十条结果，这个给你**一条结论 + 证据 + 行动清单**。

---

## Q2. 你的风险判定凭什么可信？白名单只有 8 条赛事。

**一句话**：正因为不能覆盖全部，所以它不判「真假」，只判「需不需要核实」，并把核验路径交给用户。

展开：

- 白名单是**可扩展的配置**（`data/whitelist.json`），学校可以自己往里加本校推荐赛事。
- 命中的赛事给正向分，**仅仅没命中不会直接判红**；其他高风险信号仍可能触发红色结论，避免「没见过就说是假的」。
- 真正判红的信号是**可以独立验证的**：出现「保过、交钱拿证」话术、已过截止时间、来源是群聊且无官网。

可能的追问 → 「那白名单外的正规赛事岂不是很吃亏？」答：仅仅未命中白名单不会直接判红，最终档位还要看其他来源、字段完整度和风险信号；报告会给出核验步骤。

---

## Q3. 大模型会编造信息，你怎么保证它不乱说？

**一句话**：不靠 prompt 求它别编，靠代码把它编的东西删掉。

三层机制：

| 层 | 做法 | 效果 |
|---|---|---|
| 约束 | Prompt 明确「原文没有就填 null，写进 missing_fields」 | 降低编造倾向 |
| 校验 | `evidence` 必须在原文中**逐字命中**（去空白比对），否则该字段置 null | 编造的字段当场作废 |
| 流程 | 校验不通过 → 带错误重试一次 → 仍不过就报错，不返回 | 前端看不到未过检数据 |

实测效果：示例文本里没写主办方时，界面显示「主办方：未知 · 置信度 50%」，而不是编一个「传智教育」出来。

可能的追问 → 「模型把 evidence 也编一句原文里有的空话怎么办？」答：所以还有日期合法性、conflicts 至少两个来源值、字段与 missing_fields 一致性等交叉检查。

---

## Q4. 如果模型把 11 月 20 号读成 12 月 20 号，用户信了怎么办？

**一句话**：所以每个关键字段都带原文摘录，用户能一眼对照。

展开：

- 报告里每个字段都附 `evidence` 原文句子，界面可直接比对。
- 时间类字段做格式与区间校验（2020–2035），异常值会被拦下。
- 产品定位写死：**结论由人复核**，报告底部固定免责声明。
- 这是有意的产品取舍——不追求「全自动可信」，追求「可信地辅助决策」。

---

## Q5. 为什么不微调模型，而是用 prompt + 规则？

**一句话**：一周的工期和零标注数据，微调不现实；而且判定逻辑必须可解释、可修改。

展开：

- 微调需要标注数据，我们没有；且模型换代后要重训，维护成本高。
- 规则层的好处是**可解释、可测试、可审计**：分数怎么来的，每一分都有依据，能写进文档。
- 结构上留了升级路径：`server/agents/*` 与 `server/rules/*` 解耦，将来要接更强的模型只改 agent 层。

---

## Q6. 为什么用 SSE 而不是 WebSocket？

**一句话**：数据流是单向的（服务端推、客户端收），SSE 更轻且天然适配 HTTP。

展开：

- 不需要双向通信，WebSocket 的心跳、重连、连接管理都是额外成本。
- SSE 走普通 HTTP，能过大多数代理和防火墙；`fetch` 就能读流，不依赖 `EventSource`（因为我们用 POST）。
- 踩过的坑也写在文档里：Node 16+ 中 `req.on('close')` 会在请求体读完时触发，必须监听 `res.on('close')`，否则每个请求都被误判为断开。

可能的追问 → 这个坑能讲出细节，说明真调试过。

---

## Q7. 多 Agent 是不是只是把一次调用拆成四次？又慢又贵。

**一句话**：拆分换来的是**每一步都能单独看、单独测、单独换**，这是产品需要而不是技术炫技。

展开：

- 四个节点职责不同：抽取要严（低温度、证据校验）、匹配要看得懂人（画像）、规划要算得清（工期约束）。
- 单次超长 prompt 会让模型顾此失彼；拆分后每段 prompt 只有一件事，输出更稳。
- 成本：一次完整分析约 4000–5000 token，延迟约 11 秒。**可接受，因为我们不是实时对话产品**。
- 节点拆分让状态和耗时可见；当前「重试」按钮会重跑整条链路，尚未实现单节点续跑。

可能的追问 → 「能不能并行？」答：不能，下游依赖上游输出，是严格串行链路。

## Q8. 代码是 AI 写的，你自己的贡献是什么？

**一句话**：AI 写代码，我定标准、做判断、抓错误。

具体在做的事：

- **定架构**：四段式流水线、事件契约、mock 优先策略，都是我拍的。
- **定边界**：不让模型判真假、风险优先于匹配，这类产品策略写进代码层。
- **抓错误**：SSE 零事件的排查、风险与匹配结论打架、校验器自相矛盾——三个真 bug 都是验证时发现的，不是 AI 主动报告的。
- **做取舍**：拒绝让模型判风险、拒绝为可视化引入重型图表库。

过程日志里逐条记录了这些（`docs/prompt-log/process-log.md`）。

## Q9. 用户粘贴的群聊内容会不会泄露？合规怎么考虑？

**一句话**：当前版本会把原文发给模型服务商，这一点必须在产品里讲清楚。

展开：

- 现状：文本会随请求发送给 DeepSeek API，未做脱敏。
- 已做的：`USE_MOCK` 模式可完全离线演示；`.env` 与密钥不入库；不存储用户输入（无数据库，请求结束即丢弃）。
- 改进方向：本地脱敏（手机号、微信号打码）、私有化部署、用户授权提示。

> 主动承认局限比掩盖更好——评委通常会追问这一条。

## Q10. 评测 100% 通过，能说明什么？不能说明什么？

**一句话**：能说明已知的失败模式被覆盖了；不能说明真实世界准确率。

展开：

- 12 条用例是**自建**的，覆盖诈骗、过期、冲突、注入、OCR 噪声等类别。
- 它的价值是**回归**：改一次 prompt 或规则，能立刻知道有没有把别的东西改坏。
- 局限：样本量小、非盲测、不含真实网络文本的长尾分布。
- 下一步：拿真实群聊记录做盲测，人工标注 100 条，统计字段级准确率。

## Q11. 如果明天就要上线给全校用，你还差什么？

**一句话**：差稳定性和数据，不差功能。

- **多用户**：现在无鉴权、无限流，一个人狂刷会打爆 API 额度。
- **成本**：按当前 token 消耗，1 万次分析约几十元，需要额度控制与缓存（同一赛事结果可复用）。
- **数据**：白名单要按学校维护，最好接入校内竞赛通知源。
- **错误处理**：需要重试队列、失败告警、降级到 mock。
- **合规**：隐私提示、用户授权、内容留存策略。

---

## Q12. 这个项目最难的三个技术点是什么？

1. **多 Agent 结论一致性**：风险判红、匹配却说「可试」，两个节点各说各话。解法是在编排层加硬约束——风险优先，且不交给模型决定。
2. **反幻觉的可执行化**：把「别编」这种软要求变成 evidence 逐字比对这种硬校验，并且校验失败要能重试而不是直接崩。
3. **流式链路的正确性**：SSE 的关闭语义、客户端中断、错误事件的表达方式。这类问题语法层面看不出来，只能跑起来测。
