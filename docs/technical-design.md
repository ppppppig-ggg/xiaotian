| 项目 | 说明 |
|---|---|
| 名称 | CampusRace Radar（赛博赛事雷达） |
| 赛道 | 传智杯 AI 创新应用挑战赛 · Vibe Coding |
| 文档 | 技术设计与复现说明 · 版本 1.1 · 2026-11-10 |

---

## 1. 项目概述

大学生获取赛事信息的入口分散在群聊、公众号、社交平台和赛事官网。通知中可能存在时间口径冲突、主办方信息缺失、过期报名、收费承诺或无法核实的赛事。逐条人工查找费时，直接相信单条转发又有风险。

赛博赛事雷达将一段赛事通知转成可审查的决策材料：抽取赛事字段和原文证据，按可解释规则标记风险，结合个人画像计算参赛匹配度，再生成备赛计划。最终报告给出需要人工核验的路径，不替用户认定赛事真假，也不替用户作报名决定。

## 2. 需求与产品闭环

### 2.1 目标用户与输入

- **目标用户：** 需要在有限时间内判断赛事是否值得继续核验和准备的大学生。
- **文本输入：** 公众号/微信推文、群聊消息、官方网站、社交平台文字或海报 OCR。
- **个人画像：** 专业、年级、技能栈、参赛目标、每周可投入时长。画像保存在浏览器 `localStorage`，后端会限制字段长度并将每周时长夹在 1–80 小时内。

### 2.2 用户得到的结果

1. **信息提取：** 赛事名称、主办方、赛道、报名/提交时间、链接、资格、缺失字段和证据摘录。
2. **风险核查：** 规则分数、命中白名单的事实、风险提示和人工核验步骤。
3. **个人匹配：** 技能、时间、目标价值、参赛门槛四个维度的理由和分数。
4. **备赛规划：** 是否可行、分阶段任务、里程碑与缓冲时间。
5. **结果留存：** 报告区可展开查看原文摘录，并下载 Markdown 格式的决策报告。

## 3. 总体架构

```text
浏览器输入与个人画像
        │ POST /api/analyze
        ▼
Express + SSE 编排器
        │
        ├── Extractor：LLM 结构化提取 → evidence 校验 → 失败重试一次
        ├── Fact Checker：确定性规则算分 → LLM 生成核验步骤（失败时回退模板）
        ├── Matchmaker：LLM 按画像评估四个维度 → 分数与枚举校验
        └── Planner：LLM 倒排计划 → 截止日期与工期边界检查
        │
        ▼
前端逐节点状态 + 决策报告 + Markdown 导出
```

| 模块 | 位置 | 责任 |
|---|---|---|
| 前端工作台 | `src/App.tsx`、`src/components/` | 输入、来源选择、样例、进度、画像和报告 |
| SSE 解析 | `src/lib/sse.ts` | 按事件边界解析 `data:` 行，忽略心跳注释 |
| 后端编排 | `server/index.ts` | 校验请求、顺序调用 Agent、发出节点事件、处理断连 |
| 模型适配 | `server/llm.ts` | OpenAI 兼容 Chat Completions、超时、JSON 解析和重试 |
| Prompt | `server/prompts/` | 固定角色、输入边界、Schema 和字段规则 |
| 证据验证 | `server/validate.ts` | 原文摘录、日期、缺失字段和来源冲突校验 |
| 风险规则 | `server/rules/risk.ts` | 白名单、域名边界、诈骗话术、过期和来源风险 |
| 本地资料 | `data/` | 官方赛事白名单与演示回放，不依赖数据库 |

## 4. Agent 分工与提示词工程

四个节点按依赖顺序串行执行。拆分后，每一阶段的输入、输出、耗时和状态都可以独立观察；下游可以使用前一节点已校验的数据。

### 4.1 Extractor：结构化提取

System Prompt 给出 JSON Schema 和约束：原文没写的字段填 `null`；日期统一为 `YYYY-MM-DD`；没有发布时间时不把“下周三”猜成具体日期；每个关键字段附原文摘录；群聊文本里试图改变模型要求的语句视为待分析数据，而不是系统指令。

Extractor 的用户 Prompt 将来源类型、发布时间和最多 6000 字的输入分区传入。响应先做 JSON 解析，再经 `validateExtraction` 校验。摘录不在原文、过短或不能支撑日期值时，对应字段会被置空；冲突必须保留多个来源值。校验失败时带错误列表重试一次，仍失败则返回错误事件，不把未通过的数据冒充事实。

### 4.2 Fact Checker：风险核查

风险结论由 `evaluateRisk` 的本地规则计算，模型只生成自然语言原因和核验步骤。模型不可覆盖规则分数。生成步骤失败时使用模板步骤，避免风险节点因说明文案失败而中断整条链路。

同一赛事若被规则标为红色，即使匹配 Agent 给出较高分，编排层仍把参赛建议改为“不建议”。该优先级属于产品决策，固定在代码中而不是交给模型自由判断。

### 4.3 Matchmaker 与 Planner

Matchmaker 使用明确的四维解释 Schema；服务端把分数钳位到 0–100，并限制建议枚举。Planner 使用明确的今天日期和剩余时间作为上下文，服务端再限制返回阶段数，并确保截止日期已过时直接返回不可行计划。

## 5. 确定性风险规则

初始权威度为 50，之后按可解释信号增减；总分限制为 0–100。白名单赛事名按文本匹配，官方域名使用 URL hostname 的完整边界比对，`example.org.attacker.test` 不会因包含白名单字符串而命中。

| 信号 | 分数调整 | 说明 |
|---|---:|---|
| 本地白名单命中 | +30 | 只表示本地名单有记录，不等于实时官网核验 |
| 白名单域名命中 | +15 | 仅按解析后的主机名匹配完整域名/子域名 |
| 报名链接为 HTTPS | +10 | 传输方式是正向信号，不单独证明主办方身份 |
| 报名和提交时间均明确 | +5 | 两条时间线齐全 |
| 主办方非空 | +5 | 不评价该组织实际资质 |
| 群聊/社交来源 | -15 | 非官方发布渠道，可能转述失真 |
| 缺报名 URL / 截止时间 / 主办方 | -10 / -5 / -10 | 信息缺口需要人工核实 |
| 出现诈骗承诺话术 | -30，且分数上限 39 | 防止其他正向字段抵消强诈骗信号 |
| 多来源字段冲突 | -10 | 不擅自选择一个值 |
| 截止时间已过 | -25，且分数上限 59 | 过期赛事不应显示为低风险 |
| 检出试图改写规则的提示注入 | 分数上限 79 | 该内容按普通文本处理，建议人工核对 |

阈值：`green` ≥ 80、`yellow` ≥ 60、`red` < 60。系统的表述是“低风险/待核实/高风险”，不是对赛事真假的法律或事实认定。白名单是静态 JSON，目前仅覆盖少量赛事，需由维护者核对更新。

## 6. 数据流、状态与错误路径

### 6.1 SSE 事件约定

服务端每次发送一个 JSON 事件：

```json
{"node":"extractor","status":"running"}
{"node":"extractor","status":"done","payload":{"is_event":true}}
{"node":"all","status":"done"}
```

`node` 为四个 Agent 之一或 `all`；`status` 为 `running`、`done` 或 `error`。服务端用 `res.on('close')` 观察响应断开，并定期发送 SSE 注释心跳。前端用 `AbortController` 支持用户重跑或离开页面时中止请求。无关内容在提取后短路，其余三个节点标记为跳过。

### 6.2 输入边界

- 请求 JSON 上限 64 KB；赛事文本上限 6000 字。
- 来源类型限于 `wechat`、`group_chat`、`official_site`、`social`、`poster` 和 `unknown`。
- 个人画像字段长度受限；每周投入时间限制为 1–80 小时。
- 浏览器访问 API 通过 Vite `/api` 同源代理；后端不开放任意跨站读取。
- 实时模式把赛事文本发送给 `.env` 中指定的模型服务；项目不存数据库，也不主动持久化输入文本。用户画像仅保存在当前浏览器。

### 6.3 错误处理

模型响应超时、HTTP 错误或 JSON 无效会生成有原因的错误事件。风险核验步骤可回退到模板。实时模型不可用时，用户可切换回本地样例演示；本地演示需要选择一个有固定回放数据的样例，不会把任意粘贴文本误称为模型分析结果。

## 7. 用户界面与交互

- 赛事来源可手动选择；常见通知、模糊群聊、可疑赛事和无关文本可一键载入。
- 工作流显示节点状态、进度、耗时和错误，支持键盘 `Ctrl+Enter` 开始分析。
- 报告显示抽取字段、证据摘录、风险标记、四维分数、核验步骤和计划；下载按钮导出 Markdown。
- 顶部标记“演示数据”“实时模型”或“服务未连接”；实时模式提示输入文本将发送至配置的模型服务。
- 画像缺省时可直接使用；浏览器禁用本地存储时不会阻止临时使用。
- 布局适配窄屏；动画遵守 `prefers-reduced-motion`。

## 8. 技术栈与复现步骤

前端：Vite、React、TypeScript、Tailwind。后端：Node.js、Express、TypeScript。流式通信：SSE。数据：JSON 文件和浏览器本地存储。模型：OpenAI 兼容 Chat Completions API。项目不需要数据库，也没有后台管理账号。

```powershell
git clone https://github.com/ppppppig-ggg/xiaotian.git
Set-Location xiaotian
Copy-Item .env.example .env
# 保持 USE_MOCK=true；无需填入 API Key
npm ci
npm run dev
```

打开 `http://localhost:5173`，点任意预置样例后点击「开始分析」。健康检查在 `http://localhost:8787/api/health`。更细的分步说明和排错见 `docs/reproduction.md`。

## 9. 评测记录与局限

仓库中的 `eval/cases.json` 与 `eval/report.md` 记录了 12 条自建场景：正常通知、信息缺失、诈骗、过期、来源冲突、相对时间、提示注入、英文通知、OCR 噪声和无关文本。已有报告记载 12 条用例全通过。该集合由开发者构造，规模小、非盲测，不代表真实网络文本准确率；本轮修改了风险规则，但没有重新运行评测，所以旧报告不能作为本轮代码的回归证明。更换模型、Prompt 或日期规则后也应重新运行评测。

当前版本的边界：

1. 白名单静态且覆盖面有限，系统没有联网抓取或验证官网页面。
2. 域名存在于白名单不代表当前页面或赛事公告经实时认证。
3. 模型可能漏提字段，规则也可能误报；重要信息仍需对照官方通知。
4. 实时模式没有用户认证、API 限流、额度管理或多租户隔离；不应直接暴露到公网供多人使用。
5. 每个 Agent 节点显示运行状态；当前界面“重试”会重跑整条链路，不支持从中间节点续跑。
6. 演示回放使用静态样例数据，只用于无密钥预览，不是任意用户文本的分析结果。
