## 1 项目概述与阅读导览

把信息整理，推进到参赛决策。


校园赛事雷达（CampusRace Radar）是一款面向大学生的赛事通知解析与决策辅助工具。输入零散通知和个人画像后，系统依次完成信息提取、风险核查、匹配评估、备赛规划，并输出可回溯原文的报告。


> 项目主张：先看依据，再谈建议；先核验风险，再投入备赛。


### 当前实现范围


|模块|已核对的能力|
|---|---|
|输入与呈现|文本输入、来源选择、个人画像、四节点进度、证据展开、Markdown 报告导出。|
|AI 与规则|四个串行 Agent、OpenAI 兼容模型接口、证据校验、确定性风险规则和失败降级。|
|研判台界面|封面与三区研判台、PDF/TXT/Markdown 本地导入；已随最终版本提交至评审仓库。|
|交付形态|公开代码仓库、本技术文档、5–8 分钟演示视频；本地一键复现，无需模型密钥。|

## 2 需求分析与用户场景

从“看到比赛”，到“知道下一步做什么”。


### 问题来自信息分散与决策成本


赛事通知分布在群聊、公众号、学校通知和官网中，常见问题包括截止时间口径不一致、主办方或报名入口缺失、相对时间无法定位，以及“交钱拿证”等高风险宣传。即使信息完整，学生仍需判断自身条件是否满足、备赛时间是否足够。


|用户场景|需求|系统回应|
|---|---|---|
|群聊只说“下周三截止”|识别缺失信息，避免误算日期|保留相对时间；缺发布时间时提示待核验。|
|通知含“保过保就业”|发现强风险信号|规则命中风险话术，限制分数并给核验路径。|
|有技能但时间有限|判断是否值得投入|按技能、时间、目标、门槛提供分项理由。|
|决定准备参赛|把目标拆成任务|结合截止时间输出阶段任务与里程碑。|


### 功能需求


支持输入赛事原文与来源类型；记录专业、年级、技能、目标和每周可投入时间；提取赛事基本字段及其证据；显示风险与待核验事项；输出匹配建议和计划；允许导出报告用于讨论或留档。当前本地版本还支持文本型 PDF、TXT 和 Markdown 的浏览器内导入。


### 非功能需求


输出可解释、失败可见、配置可复现、演示不依赖模型额度。模型结果须经过代码校验，空信息应明确呈现；界面通过逐节点事件展示进度；演示模式与实时模型模式应清楚区分。


> 验收方式：输入一条通知后，用户应能找到关键信息的出处、需要核对的事项、适合自己的理由，以及下一步可执行的动作。当前价值判断来自产品设计与样例验证，尚无大规模用户研究。


## 3 系统架构与数据流

四段串行，让每一步有独立的职责。


浏览器 → 四节点串行编排 → 报告；规则与校验贯穿流程。


|层次|实现|作用|
|---|---|---|
|表现层|React 19、Vite 8、TypeScript 7、Tailwind 4|输入、画像、节点状态、证据与报告展示。|
|编排层|Node.js、Express 5、SSE|请求校验、顺序调度、心跳、断连与错误事件。|
|AI 层|agents/、prompts/、llm.ts|结构抽取、解释、匹配和任务拆解。|
|规则与校验层|validate.ts、rules/risk.ts|证据命中、日期边界、风险规则与业务硬约束。|
|数据层|data/ 中的 JSON 文件|赛事白名单与预置演示数据，无数据库。|


### 数据如何流动


前端向 POST /api/analyze 提交 text、sourceType、sampleId 与画像字段。后端先校验输入，再串行运行四个节点；每个节点发送 running/done 状态与 payload，最后通过 node=all 发送结束或错误事件。前端读取流并更新节点与报告。GET /api/health 用于确认服务和 mock/live 模式。


### 为什么采用串行链路


下游节点依赖已整理的赛事对象，每段可独立约束输入、检查输出并定位失败；代价是累积延迟与模型成本。四节点是程序编排的任务链，不宣称是自主智能体网络。


## 4 信息提取与证据校验

模型负责理解，程序负责检查。


### 抽取对象与输出边界


Extractor 将非结构化文本转为固定 JSON，包含 is_event、赛事对象、evidence、missing_fields、conflicts、warnings 和 injection_detected 等字段。缺失信息按提示词要求留空；相对时间缺少发布时间时不应推算成确定日期。


|机制|代码行为|作用与边界|
|---|---|---|
|证据匹配|去除空白后，检查已提供的摘录是否出现在原文中。|验证引用出处；不能单独证明引用支持字段语义。|
|片段长度|有效摘录少于 6 字时判错并置空字段。|减少短片段冒充依据。|
|日期检查|日期字段的证据须包含日期值，且日期在合理年份内。|格式差异仍可能触发误拒绝。|
|冲突检查|声明冲突时至少需要两个来源值。|检查结构，尚非全面的语义冲突验证。|
|缺失统计|关键空字段与 missing_fields 数量不一致时添加警告。|这是软检查，未强制所有非空字段均附证据。|


### 重试与失败策略


extractor.ts 对校验失败结果带错误清单重试一次；再次校验失败则抛出错误，编排层发送失败事件。校验失败的结果不直接展示为成功报告。当前 JSON 解析等调用异常会直接进入错误处理，不能把“所有异常都自动重试”作为已实现能力。


> 可信度边界：证据校验检查的是摘录命中与部分字段约束，尚未全面覆盖“每一个非空值都有依据”及“值与引文在语义上严格一致”。因此可以说降低无依据输出风险，不能说已经消除模型幻觉。


### 后续加强方向


后续将为关键非空字段强制 evidence，并补充语义一致性、运行时 Schema 与日期边界测试。


## 5 风险核查与 AI 约束

风险结论由规则计算，解释由模型补充。


### 风险判定的执行过程


Fact-Checker 先调用 evaluateRisk()，综合本地白名单、域名、通知来源、关键信息缺失、营销话术、冲突、过期和提示注入等信号，输出 authority_score、verdict、risk_flags 与 fallback_steps。随后调用模型生成可执行核验说明；模型失败则使用规则内置步骤。


|约束|当前实现|
|---|---|
|显示档位|规则分数 ≥80 为绿，60-79 为黄，<60 为红；分数是规则指标，不是真实概率。|
|强风险话术|命中相应关键词时分数上限为 39，不能被白名单等正向项抵消到低风险。|
|提示注入|模型标记或规则正则命中后，分数上限为 79，避免输出低风险。|
|截止已过|依据当前时间检查过期信号，分数上限为 59。|
|风险优先|若风险为红，编排层强制把匹配建议调整为“不建议”。|


### 输入中的指令不改变分析规则


Prompt 将用户原文放在明确的数据边界内，并要求忽略“给我 100 分”等注入指令；规则层另行检测，避免完全依赖模型自报。输入仍属于待分析资料，不能成为修改系统规则的授权。正则覆盖有限，尚不能声称抵御所有注入。


> 本系统没有实时联网核验赛事的能力。白名单匹配和风险规则用于提示核验方向；“低风险”不等于官方认证，“高风险”也可能包含已过期等因素，应结合具体标签理解。


### 人工核验闭环


建议用户打开主办方官方渠道核对本届赛事、核查报名入口与时间，并向校内竞赛负责老师确认。系统把“需要核实”转为清晰动作，保留由人做最终判断的过程。


## 6 个人匹配与备赛计划

从通用信息，走向与个人条件相关的行动。


### 匹配评估


Matchmaker 接收结构化赛事对象和个人画像，输出 0-100 的匹配分、四维理由、建议档位、硬门槛及下一步动作。Prompt 约定技能 40%、时间 30%、目标价值 20%、门槛 10%。


|维度|所回答的问题|实现说明|
|---|---|---|
|技能匹配|赛事要求是否与现有能力重合？|模型输出分项分数和理由。|
|时间充裕度|距离截止的准备时间是否足够？|综合时间与每周投入给出建议。|
|目标价值|对作品集、求职或兴趣是否有帮助？|不把宣传承诺当作实际收益保证。|
|门槛可达|专业、年级、队伍等条件是否满足？|列出无法绕开的限制条件。|


服务端对分数进行 0-100 钳位并检查推荐枚举。当前总分沿用模型输出，没有在代码中严格重算四维加权，也没有覆盖所有硬门槛逻辑；这些属于需要进一步工程化的约束。


### 备赛计划


Planner 优先使用作品提交截止时间，否则使用报名截止时间；根据剩余周数、画像和匹配结论生成阶段、任务、成果物和里程碑。总周数限制在剩余时间内，阶段最多 6 个、每阶段最多 4 个任务、里程碑最多 5 个。


> 时间校验的局限：当前使用向上取整的剩余周数判断截止，刚刚过期、但未满一周的边界需进一步测试；总周数受限，也不等于每个阶段与缓冲周在语义上完全一致。计划应由用户结合实际截止时刻复核。


### 用户价值


匹配分提供比较入口，分项理由帮助理解差距，计划把“适合参加”转成“这周先完成什么”。这些输出是辅助建议，尚未通过独立用户研究证明能提升获奖率或节省固定比例的时间。

## 9 AI 技术选型与优化策略

把每项选择对应到具体任务。


|选择|理由|实现方式|
|---|---|---|
|大模型理解非结构化文本|通知格式多变，规则难穷举。|通过 OpenAI 兼容的 chat completions 协议调用。|
|四个任务节点|抽取、核查、匹配、规划的输出目标不同。|独立 Prompt 与 Agent 文件，编排层串行调用。|
|确定性规则|风险分数与业务约束需要可检查。|risk.ts 独立计算，编排层落实风险优先。|
|结构化输出|前端需要稳定字段，便于校验。|请求 JSON 格式；Prompt 给 Schema，代码执行部分校验。|
|SSE|界面需要逐节点状态，通信以服务端推送为主。|事件流、15 秒心跳与断连检测。|
|静态 JSON|原型阶段数据规模小，便于复现。|赛事白名单与固定回放存储在 data/。|


### 参数与集成


环境变量使用 LLM_API_KEY、LLM_BASE_URL、LLM_MODEL 控制服务商和模型；.env.example 以兼容服务为示例。不能因兼容协议就将项目写成固定使用某个 OpenAI 模型。模型调用默认超时 45 秒，抽取温度 0.1，核查解释 0.2，匹配与规划 0.3。


### 已有优化


下游优先消费结构化对象以减少无关上下文；非赛事内容尽早短路；校验失败附错误反馈；风险解释失败回退规则模板；演示模式不消耗模型额度。模型回复的 JSON 解析支持清理围栏与尝试提取对象。


### 进一步优化


首先完善字段级证据覆盖、分数重算和时间边界，再用更大测试集评估模型、Prompt 和成本。缓存、并行化、检索增强与更小模型替换是可研究方向，当前尚未实现，不作为已验证的降本或提速成果。


## 10 运行复现与部署方案

先让评委复现，再谈长期在线服务。


### 本地演示


```bash
git clone https://github.com/ppppppig-ggg/xiaotian.git
cd xiaotian
npm ci
# 将 .env.example 复制为 .env，保持 USE_MOCK=true
npm run dev
```


前端默认 http://localhost:5173，后端默认 http://localhost:8787。先检查 /api/health 返回 ok=true 和 mode=mock，再选择预置样例进行演示。依赖以 Vite 8 为基线，建议使用 Node.js 22.12+ 的兼容 LTS 环境；本次构建与截图使用 Node.js v26.13.0。


### 两种运行模式


|模式|行为|适用范围|
|---|---|---|
|USE_MOCK=true|只回放四个预置样例，无模型调用。|现场讲解、断网展示、验证界面流程。|
|USE_MOCK=false|分析自定义文本，使用配置的模型服务。|真实分析与批量模型评测，需服务可用和额度。|
|本地复现（推荐）|按上方命令启动，默认演示模式。|评审现场、无网络环境。|


### 公网产品部署建议（尚未执行）


前端通过 npm run build 生成 dist；后端需独立 Node 服务运行，反向代理将 /api 指向后端。为 SSE 关闭代理缓冲、设置足够的读取超时；使用 HTTPS 和服务端环境变量保管密钥。上线前增加访问限流、请求并发控制、日志脱敏与健康监控。仅发布 dist 到 GitHub Pages 无法运行 Express 或实时模型链路。


> 数据说明：文件导入在浏览器本地解析；实时模式会将提取后的分析文本与画像发送至后端和配置的模型服务。后端未实现数据库持久化，但这不代表第三方服务没有日志或留存。当前身份认证、多人账号与生产级访问控制未实现。


## 11 技术创新与应用创新

创新重点是组合方式与可复核的决策过程。


### 技术创新点：让关键约束进入代码


|设计|与直接问答相比的价值|可核对的实现|
|---|---|---|
|分阶段结构化链路|每步可见、可定位，不把所有判断塞进一段回复。|agents/、prompts/、server/index.ts。|
|抽取与证据联动|把原文依据作为检查对象，失败结果不直接当成功。|validate.ts 与 extractor.ts。|
|规则决定风险|让风险结论脱离模型自由生成，保留可复现规则。|rules/risk.ts、fact-checker.ts。|
|风险优先于匹配|避免“很适合我”掩盖风险信号。|编排层对红色风险调整推荐。|
|故障可见与降级|核查说明可回退，错误通过事件显式传递。|模板步骤、SSE 错误事件、故障测试。|


### 应用创新点：围绕大学生的参赛决策


项目将“通知解析”与“个人条件”“备赛任务”连接起来，覆盖从看到信息、发现疑点到安排准备的完整过程。四维理由比单一分数更便于讨论，核验路径比简单的真假结论更容易执行。


### 创新表述的边界


本项目是基于现有大模型、Web 技术与规则校验的应用整合，并未训练自有基础模型，也未证明首创性或建立全球赛事认证体系。创新点应以可运行机制和真实使用情境说明，不使用“行业首创”“杜绝幻觉”等缺乏证据的表述。


> 适合答辩的一句话：我的创新不是让 AI 多给一句建议，而是把赛事分析拆成可检查的步骤，让关键结论有证据、风险有规则、准备有行动。


## 12 局限、演进路线与项目理念

先补强可靠性，再扩大使用范围。


|当前局限|可执行的下一步|
|---|---|
|白名单有限，无法实时核验|建立来源维护流程，研究有出处的官方信息检索。|
|证据与 Schema 检查不完整|强制关键字段证据，补足语义与结构验证。|
|匹配总分由模型给出|代码重算四维权重，统一硬门槛和推荐阈值。|
|时间与计划仍有边界|按截止时刻直接判断过期，检查阶段、缓冲与周数。|
|缺少真实用户验证|收集同意后的匿名样本，独立标注并开展小规模试用。|
|服务部署尚未完成|补齐限流、监控、密钥管理和评审可用性检查。|


### 建议演进顺序


第一阶段：统一源码与文档，补齐证据覆盖、时间边界和评分一致性，形成可重复回归集。第二阶段：录制真实端到端演示，测试不同专业与不同时间预算的场景。第三阶段：在授权数据来源上增加检索和来源更新时间，逐步开展校内试用。第四阶段：依据试用反馈决定是否建设收藏、提醒与协作功能。以上是规划，不是已完成承诺。


### 项目想法说明


我做“校园赛事雷达”，是因为大学生面对的往往不是比赛太少，而是信息太散、真假难辨，也不知道该把时间投入哪一场。我希望把群聊、公众号和官网里的零散通知，整理成一份有原文依据的参赛决策报告：先提取赛事信息，再提示需要核验的风险，结合个人专业、技能和时间判断是否适合，最后给出可以执行的备赛计划。项目采用四个分工明确的 AI 节点，同时用代码校验原文证据、约束风险结论，让建议更透明、也更容易复核。我希望它能帮助同学少花时间辨别信息，把精力用在真正适合自己的比赛和作品上。


> 我希望项目帮助同学把“我听说有个比赛”，变成“我知道要核对什么，也知道下一步该做什么”。
